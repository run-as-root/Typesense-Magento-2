# Changelog

All notable changes to this project are documented in this file.

## [Unreleased]

### Added

- Attribute sort options: Instant Search > Sort Options offers both directions of every product attribute with "Used for Sorting in Product Listing" = Yes (`attr:<code>:asc|desc`, e.g. `attr:volume_percent:asc` for "Alkohol Vol.-%", as on ElasticSuite). Each such attribute is indexed with a single-valued sortable companion field `<code>_sort` (Typesense cannot sort the `string[]` attribute fields): `float` when the attribute stores numbers or all its option labels are numbers with an optional unit, else `string`; the product's own value, or for a composite product without one the lowest value of its children. The option is labelled with the attribute's store label, follows a category's available sort-by list, and a category whose default sort is the attribute opens with it ascending. New `SortOptionProvider` (`ListingConfigViewModel` takes it), `SortableAttributeProvider` (`ProductSchemaProvider`, `AttributeResolver` and `ProductDataBuilder` take it) and `TypeSenseConfigInterface::getSortOptionKeys()`; `getEnabledSortOptions()` is deprecated and returns only the fixed options.
- Search > Exhaustive Search (`run_as_root_typesense/search/exhaustive_search`, default No): sends `exhaustive_search` with every storefront product search (listing, its facet and direct-match copies, header search). Typesense otherwise stops considering token variants (typos, prefixes) once it found enough matches; on a store with ~430 products "marille" finds 54 products by default and 83 with it on. Larger catalogs can raise `max_candidates` instead (README, Search Settings).
- Indexing > Enable Customer / Order / Store / System Configuration Indexing (`run_as_root_typesense/indexing/{customer,order,store,system_config}_enabled`, default No) and `bin/magento typesense:collection:delete --entity=<type> --force`, which deletes the aliases and collections of a disabled entity type in every store view.
- `bin/magento typesense:suggestions:seed [--limit=N] [--store=<code>]` imports the top N Magento search terms per store view (`search_query` with `num_results > 0` and `is_active = 1`, by popularity, one `LIMIT` query; N defaults to and is capped at the new Suggestion Limit) into the suggestion collections as `{id, q, count}`, under the id Typesense analytics give the same query (wyhash of the normalized query), so later counts add to the seeded document. `action=create` keeps documents already present, so it can run again.
- Indexing > Suggestion Limit (`run_as_root_typesense/indexing/suggestion_limit`, default 1000): how many popular queries a store's suggestion collection keeps.
- Suggestion abuse protection (README, "Abuse protection"): visitors can make Typesense count any text, so suggestion documents get an optional `is_valid` flag set by a check (`SuggestionPruner`) that searches each term on the store's product collection like the search page; terms containing a blocked word (new Blocked Suggestion Words), longer than the new Suggestion Maximum Length (60), with `@`, `://`, `www.` or mostly non-letters are deleted. The check runs after every suggestion reindex and seed and by the new cron job `typesense_suggestion_prune` (Suggestion Check Schedule, `20 * * * *`), at most Suggestion Limit documents per store. The storefront shows only `is_valid:=true && count:>=<Suggestion Minimum Count>` (default 3) and repeats the term rules and blocked words in the browser (`suggestionAllowed()`). The visitor id is documented as no trust boundary.
- `Api\SelfMaintainedEntityInterface` for entity indexers whose documents Typesense writes itself: a full reindex calls `provision()` instead of rebuilding or swapping the collection, partial reindexes do nothing.
- `bin/magento typesense:import:elasticsuite [--synonyms] [--boosts] [--positions] [--dry-run] [--store=<code>]` migrates ElasticSuite's own data (README, "Migrating from ElasticSuite"). It reads the `smile_*` tables directly (ElasticSuite's code need not be installed; missing tables skip their section with a message), prints per section what was created, updated, left unchanged and skipped with the reason, and re-runs update instead of duplicating. Thesauri become synonyms of the product and (where categories are indexed) category collections of their store views, keyed `es-thesaurus-<id>-<term_id>`: every term_id group of a synonym thesaurus a multi-way synonym (single-term groups, which had no effect in ElasticSuite, are skipped), every expansion a one-way synonym from its reference term to the expanded terms. Constant-score optimizers become boosting rules named `ES optimizer #<id>: <name>` with the score value as weight and the condition tree converted to the module's conditions where an exact equivalent exists (SKU "contains" becomes "is one of" the SKUs containing the value as whole words, listed in the summary); optimizers limited to certain queries or categories are created inactive for review, other models and conditions (e.g. stock) are skipped. "All store views" merchandiser positions become Magento category positions (positioned products first, the other assigned products behind them in their Magento order; products an anchor category only inherits are assigned to it to hold their position), blacklisted products become "hide" rows of the category merchandiser; store-view-specific positions are reported, as Magento positions are global. Upgrade note: run a full product reindex after importing positions.
- Category listings follow the Magento category positions when sorted by "position" (Magento's default, or the category's default sort; the relevance option on category pages), which used to fall back to relevance: product documents get a sortable `category_position_<id>` int32 field per category in `category_ids` (schema pattern field `category_position_.*`), loaded from `catalog_category_product` once per indexing batch, with anchor-inherited products after the category's own ones (lowest subcategory position + 10000, as in Magento's category product index). The sort is `category_position_<id>:asc` followed by the category boosting rules, after `in_stock:desc` when out-of-stock products go last. Until the collection has the category's field (built before the upgrade, or a category without indexed products) the previous relevance sort stays, since Typesense fails a sort on an unknown field; the field names are read from Typesense and cached for five minutes. `ProductEntityIndexer` takes the new `CategoryPositionResolver` and `ListingConfigViewModel` the new `CategoryPositionSortBuilder` as constructor arguments. Upgrade note: full product reindex required; without Zero-Downtime Reindex delete the product collections first (`typesense:collection:delete`), because the pattern field is only added when a collection is created.

- Active boosting rules now apply to relevance sorting on the search page, in autocomplete and on Typesense category listings: `sort_by` becomes `_text_match(buckets: N):desc,_eval([(<rule filter>):<weight>, …]):desc`, with the store's active, in-window rules for that context. ### Changed

- Search suggestions and popular searches come from Typesense 29 search analytics instead of an export of Magento's `search_query` table (README, "Search Suggestions"). The full export loaded every term with results per store into memory and also carried one-off junk; terms first searched on the Typesense search page were never exported, because Magento only raises their popularity, not `num_results`. The `typesense_suggestion` indexer now creates per store view the collection `<prefix>_suggestion_<store>` (`q` string, `count` int32; not versioned, existing documents are kept) and the `popular_queries` rule `<prefix>_suggestion_<store>_popular` from the product alias (`expand_query: true`, `limit` = Suggestion Limit; written only when missing or changed), and seeds a newly created collection. Typesense counts only queries with results. Partial suggestion reindexes are no-ops. The rule uses the Typesense 29 format; Typesense 30 changed it.
- Storefront searches send the visitor id `x-typesense-user-id` (random, `localStorage` key `typesense-visitor-id`) as multi_search URL parameter, so Typesense groups keystrokes per visitor rather than per proxy IP, and `enable_analytics: false` on every search but the typed product query (header search) and the search page's main search on page load: `q=*` listings, facet and direct-match copies, paging/sorting/filtering, cross-sells, no-results products, recommendations, suggestion and popular-search lookups, admin and AI assistant searches. Suggestions are searched with `query_by: q`, popular searches sorted by `count:desc`, rows read `q`. `listing-core.js` exposes `visitorId()` and `searchParams(config)`; `buildSearches(state, config, recordQuery)` has a third argument.
- Breaking for customisations: `SuggestionDataBuilder` is removed, `SuggestionEntityIndexer` takes the provisioner, seeder, config and logger, and `SuggestionSchemaProvider` returns `q`/`count`.

### Fixed

- Listing URLs with Magento's page parameter (`?p=2`, used by old links, sitemaps and Magento's pager) open that page instead of page 1: `parseUrlState()` reads `p` as `page` when no `page` parameter is present, and the URL is rewritten with `page`. The cacheable search page accepts `p` as a listing parameter.
- A full reindex that changes a collection's schema (a new or changed field, e.g. the sortable `name`, a new sort or searchable field, or a new category position field) now cleans the full page cache and forgets `CollectionFieldProvider`'s cached field list of that collection, so cached category and search pages stop sending `query_by`/`sort_by` built for the old schema. The schema of the new collection is compared with the previously live one (a first build or a newly created collection counts as changed); the cache is cleaned once per `reindex()` call, also when a later store view fails, the same way saving a boosting rule does. `ZeroDowntimeService::finishReindex()` returns whether the schema changed; `IndexerOrchestrator` takes the new `SchemaChangeHandler`.
- A zero-downtime reindex no longer swaps the alias to a collection the synonyms or merchandising overrides could not be re-created on: the failure was only logged, so synonyms and curations silently disappeared from the live search. `ZeroDowntimeService::finishReindex()` now runs every applier, and when one fails while a live collection exists it throws `ApplierFailedException` before the swap; the old collection stays live, the orchestrator deletes the new one and rethrows, so `typesense:reindex` exits non-zero and the cron logs the error. The first build of a collection (no alias yet) still goes live and only logs the failure. Restores the Ceymox order of copying synonyms before switching the alias.
- The "Name: A–Z"/"Name: Z–A" sort options and categories whose default sort is Name work: the product schema declared `name` without `sort: true`, so Typesense answered `sort_by=name:asc` with 400 "Could not find a field named `name` in the schema for sorting" and the listing showed its error state. Every other offered sort option sorts by a numeric field.
- The indexing flags are respected: every full reindex (cron, queue, `typesense:reindex` without `--entity`) and every mview update indexed all registered entity types, so customers and orders (names, e-mail and postal addresses) were copied into Typesense nightly and on every save although only the admin assistant reads them. An entity type is now indexed in a store only when `indexing/<entity type>_enabled` is on there; entity types of other modules without such a flag stay indexed. `typesense:reindex --entity=customer` with the flag off prints a skip message, and the assistant's `search_typesense` tool answers with an error for a collection that is not indexed or missing. `IndexerOrchestrator` takes the new `IndexableStoreResolver` instead of the store repository.
- README: the Query Merchandiser is under Stores > TypeSense (the admin menu lives under Stores), not Content > TypeSense.
- A CMS page whose content fails to render (e.g. a broken Hyvä CMS component throwing a `TypeError` while `typesense:reindex` renders content in the frontend area) no longer aborts the whole reindex: the page is indexed with its stored content and a warning is logged. Script and style contents are no longer indexed as page text.
- Category documents hold the URL of the store being indexed. The category's URL instance is Magento's shared frontend URL object, which kept the base URL of the first store that used it, so the autocomplete linked every store's categories to that store. Upgrade note: reindex categories (`bin/magento typesense:reindex --entity=category`).
- The price slider no longer shows a 0-1 range when every result has the same price (e.g. all 0.90): the rounded stats of a single price now have min equal to max, so the slider is hidden as in ElasticSuite.
- The search page no longer shows facets of attributes whose "Use in Search Results Layered Navigation" (`is_filterable_in_search`) is No, as in Magento and ElasticSuite. Category pages are unchanged. `FacetConfigBuilder::build()` takes an optional `$isSearchPage` argument.
- Each store view's category collection held the categories of every root category, so on a multi-brand install the header search offered another brand's categories, with URLs that did not work in that store. It now holds only the active categories below the store's root category, with the URL of that store view; a partial reindex deletes categories of another root from the collection. Upgrade note: run a full category reindex (`bin/magento typesense:reindex --entity=category`); without Zero-Downtime Reindex delete the category collections first (`typesense:collection:delete`), because a full reindex into an existing collection does not remove the foreign categories.
- A quantity typed into a grouped tile's size row is rounded up to the next multiple of that size's quantity increment (on `change`, written back into the input); a non-multiple was rejected by the cart, which redirected to the product page.
- A malformed "Facet Types" or "Searchable Attributes" config value (not valid JSON, e.g. hand-edited or PHP-serialized) is treated as unset instead of throwing, which failed every listing and search page with a 500.
- A configured facet whose field is missing from the product schema or not faceted (e.g. an attribute removed from "Additional Attributes to Index") is left out of the listing config: Typesense rejected the facet search with a 400, so every other facet disappeared, and with its URL parameter set the whole listing showed the error state.
- The CSP `connect-src` allowlist now includes the search node the browser actually connects to (`general/search_host`/`search_port`/`search_protocol`, falling back to the indexing node) besides the indexing node; with a separate public search host, storefront Typesense requests were blocked under a restrictive CSP.
- Product recommendations ("You May Also Like") are a CSP-safe Alpine slider (`initTypesenseRecommendations` with one `initTypesenseRecommendation` per tile) rendered with `x-for`/`x-text`/attribute bindings instead of `innerHTML`, so document names and URLs can no longer inject markup or attributes; prices use `hyva.formatPrice` (no more hardcoded `$`) and follow the new `RecommendationsConfigViewModel::canShowPrices()` (plug it like the listing's). The view model's config no longer carries the Typesense host, port, protocol and key: requests use the shared `getClient()`. Strings are translated in `de_DE.csv`.
- Grouped tiles add the chosen sizes to the cart again: `buildCartParams()` takes the tile's child ids as a fifth argument and sends every child in `super_group`, unselected ones as 0, as the product page does; Magento answered a partial `super_group` with "Please specify the quantity of product(s)".
- An additional attribute named like a core product field (e.g. `short_description`, set through a config import that bypasses the admin list) no longer fails the product reindex with "duplicate field names in the schema"; the core field is kept.
- Additional attributes named like any product document field (including `is_new`, `in_stock`, `sales_count`, `category_ids`, `children`, `categories_text`, `name_decompounded` and `embedding`) are no longer offered in the admin, are skipped in the schema and are never indexed: previously a Yes/No `is_new` attribute replaced the core boolean with "Yes" and Typesense silently dropped the product, and a `category_ids` attribute overwrote the category ids. The list is `ProductSchemaProvider::RESERVED_FIELDS`; core values always win over additional attributes in the document.
- Category path facets are hierarchical: each product now carries the path of every ancestor of its categories at that ancestor's level (`categories.lvl0` top-level name, `categories.lvl1` "A > B", `categories.lvl2` "A > B > C" and every deeper path), so a parent category's value counts its whole subtree, as the subcategory filter needs. The store root and root catalog no longer appear in `categories.lvl0`. `category_ids` also holds the anchor ancestors of each assigned category, following Magento's anchor index (an active assigned category adds every active anchor ancestor, also above a non-anchor one; the store root is not added), so Typesense category pages, the category merchandiser and the "No Results" suggested products of an anchor category now list the products of its whole subtree, as Magento does. Category names, paths and anchor membership are read per indexed store (the category cache is per store), and inactive categories add no name and no path (an inactive assigned category adds nothing for its ancestors either; its own id stays in `category_ids`). Upgrade note: run a full product reindex.
- With instant search disabled (or the module off), the search page keeps Magento's own results again: the Typesense search layout moved from `catalogsearch_result_index.xml` to the `typesense_search_result` handle, which `LayoutLoadBefore` adds only while both are enabled.
- A virtual category whose rule contains `||` keeps its merchandising (pins/hides) on the storefront: the listing no longer wraps the category filter in extra parentheses when no facet is active, so `filter_by` equals the override rule again.
- The search page, autocomplete and category listing configs are JSON-encoded with `JSON_HEX_TAG | JSON_HEX_AMP | JSON_HEX_APOS | JSON_HEX_QUOT`, so admin-entered values (e.g. boosting rule conditions containing `</script>` or `<!--`) cannot break the inline script.
- Partial reindexes (mview/`executeList`) no longer build a new collection and swap the alias to it; they upsert into the live alias and skip with a log when no index exists yet.
- Partial reindexes delete documents for entities that are disabled, removed from the store's website, not visible, or deleted; document ids are mapped per entity type (`EntityIndexerInterface::getDocumentId()`), so prefixed ids (customers, orders, stores, config) are removed too.
- Changing a child product re-syncs its parent products (configurable, grouped, bundle) via `catalog_product_relation`.
- Products are indexed only into the collections of stores whose website they belong to; inactive stores and stores with TypeSense disabled are skipped; indexing runs inside store emulation.
- Autocomplete suggestions query the `query` field (previously the non-existent `q`).
- Synonyms and category/query merchandising overrides survive zero-downtime reindexes: they are re-applied to the new collection before the alias swap.
- Category merchandising pins/hides apply again: the storefront category listing and the override `rule.filter_by` are built by one `CategoryListingFilterBuilder` (category filter + `visibility:[2,4]`), since Typesense matches override filters exactly.
- `typesense_product` mview subscribes to `catalog_product_website` and `catalog_product_relation` (`parent_id`), so removing a product from a website or changing a parent's children triggers a partial reindex.
- Product visibility is filtered on the attribute, not via `catalog_category_product_index`, so a stale category index no longer decides what is indexed and products without a category are indexed.
- Every mview indexer ignores an empty id list instead of running a full reindex.
- A store enabled only at store-view scope is indexed even when TypeSense is disabled at default scope.
- A failed zero-downtime build deletes its half-built collection instead of leaving it behind.
- Deleting a synonym removes it from Typesense first; a Typesense failure leaves the stored synonym intact.

### Added

- `run_as_root_typesense_synonym` table; admin synonyms are persisted in Magento and pushed to Typesense.
- `typesense:collection:rollback --entity=<type> --store=<code>` points an alias back to the previous collection version.
- Partial product reindexes go through the `typesense.reindex` message queue when queue reindex is enabled (message carries `entity_ids`).

The search page, autocomplete products and category listings send them from one `SearchRequestParamsBuilder`; "Enable Typo Tolerance" now sets `num_typos` (2 or 0).

### Changed

- The listing's category facet filters by category id instead of the `categories.lvlN` path strings, as Magento's layered navigation and ElasticSuite do (`?cat=12`): path values made long URLs that broke when a category was renamed. Category pages list the children of the current category, the search page the store root's top-level categories, following Magento's category filter (active in the store, position order, store-view names, nothing below an inactive category, only children in the current result that narrow it; a selected one always stays). A category without children has no category facet; before, it fell back to a generic "Category" facet of the shop's top-level categories, whose selected value showed only as a chip. The facet (`Model\Listing\CategoryFacetResolver`, type `category`) lists its categories as `values` (`[{value, label}]`) in the listing JSON config, so chips and options show names, and sets `maxValues` to the number of categories: products also carry their ancestors and categories of other trees, which could push the children out of Typesense's `max_facet_values` most frequent values, so the facet always gets its own search with that limit. `listing-core.js` gains two generic facet keys: `param` (URL key, else the field name) and `values` (the only values offered and accepted from the URL, in that order and with those labels); facet count entries carry the `found` of their search. `TypeSenseConfig::getFacetFilters()` no longer prepends `categories.lvl0` and drops duplicates; `FacetConfigBuilder` ignores `categories.lvl0`/`lvl1`/`lvl2` and `category_ids` in "Facet Filters", since the category facet is always added first. The `categories.lvlN` fields stay indexed. Breaking for themes: `SubcategoryFacetResolver`, the `subcategory` facet type and `prefix` are removed; the slot `typesense.listing.filters.subcategory` (`listing/filters/subcategory.phtml`, `subcategoryFacets()`) is now `typesense.listing.filters.category` (`listing/filters/category.phtml`, `categoryFacets()`), and the category and search layouts no longer set `filter_chip_widths`. GA4 `filter_interaction` events report the category id as `filter_value`.
- Every additional attribute is a `string[]` field (single selects, booleans and text attributes were `string`), because a composite parent can hold several values. `AttributeResolverInterface::getExtraAttributes()` returns a list of strings per attribute, `getMultiselectAttributeCodes()` is removed and `ProductSchemaProvider` no longer takes an `AttributeResolverInterface`. Themes or plugins that read such a field from a document as a string must accept an array.
- The Alpine components of the filters and toolbar slots moved out of `listing/filters/{bar,mobile-drawer,dropdown,checkbox,slider,active-filters,sorting,page-size}.phtml` into `listing/script/filters/*.phtml`, rendered by the new `typesense.listing.script.filters` container under `typesense.listing.script`, so those slot templates are markup-only and a theme can override, move or remove them without copying JavaScript. Component names and behaviour are unchanged. Breaking for customisations: a theme copy of one of these templates that changed its inline script is now overridden by the module's script (it renders later); move such changes to a theme copy of `listing/script/filters/<name>.phtml`.
- `composer.json` now requires `magento/module-inventory-sales-api` and `magento/module-inventory-configuration-api` (`^1.2`; Mage-OS packages replace them), which the product indexer calls for salable stock and quantity increments.
- Breaking for customisations: `ProductSchemaProviderInterface` now extends `Api\CollectionSettingsProviderInterface`, so a custom implementation (preference) must add `getCollectionSettings(): array` and return at least `['enable_nested_fields' => true]` for the grouped `children` field. `ProductEntityIndexer` also implements `CollectionSettingsProviderInterface`; other entity indexers may implement it to set collection-level schema options.
- Breaking for customisations: `ViewModel\Frontend\CategorySearchConfigViewModel` is removed and `InstantSearchConfigViewModel` keeps only `isEnabled()`; the listing configuration comes from `ViewModel\Frontend\ListingConfigViewModel::getConfig('search'|'category')`. `ProductDataBuilder` takes a new `NewProductResolverInterface` constructor argument. `view/frontend/web/css/instant-search.css` and the search page's direct-matches block are removed. Conversational search on the search page now shows its answer above the keyword results; the product grid always comes from the keyword search, so facets and paging stay consistent.
- `openai-php/client` constraint widened to `^0.19 || ^0.20` (installs that already lock 0.20 can require the module).
- Product collections now include "Catalog" visibility; the search page and autocomplete filter `visibility:[3,4]`, category listings `visibility:[2,4]`.
- Zero-downtime cleanup keeps the new collection and the one the alias pointed at before the swap (the rollback target) and deletes every other version. Rollback moves to the highest lower version, or to the other remaining version when none is lower.
- A plain (non-versioned) collection that has the alias name is replaced by a versioned collection + alias on the next full reindex.
- `typesense_product` mview batch size is 200; the reindex consumer processes up to 100 messages per run.
- `EntityIndexerInterface` has a new method `getDocumentId(int $entityId): string` — custom indexers must implement it.
- Removed the unused "Minimum Word Length for Typo Tolerance" setting (`search/typo_tolerance_min_word_length`); use the new per-typo minimum word lengths.
- Removed the unused `view/frontend/web/js/instant-search.js` and `autocomplete.js` (the templates carry their own inline scripts).
- `TypeSenseConfigInterface` has new search-parameter getters, and the instant search, autocomplete and category search ViewModels take `SearchRequestParamsBuilder` and `SearchParametersProvider` as new constructor arguments — custom implementations or subclasses must be updated.

- **Full product reindex required** after adding an attribute sort option (`bin/magento typesense:reindex --entity=product`): until then the option sorts by a field the live collection lacks and the listing shows its error state.
